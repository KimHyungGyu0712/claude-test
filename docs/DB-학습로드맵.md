# DB(데이터베이스) 학습 로드맵 — 이 프로젝트에 맞춘 순서

- **작성일:** 2026-09-05
- **대상:** 개발 입문자. 이 프로젝트는 Firebase Cloud Firestore를 쓰지만, 나중에 일반적인 DB(SQL)까지 배울 수 있게 단계를 이어 놓았다.
- **원칙:** 이론을 먼저 외우지 않는다. **이 앱의 데이터(학생, 벌점, 도시락…)** 를 예로 삼아, 필요해지는 순서대로 배운다.

---

## 전체 그림 — DB는 왜 필요한가

앱은 화면만 보여 준다. 화면을 닫거나 새로고침하면 앱 안의 값은 사라진다.
**어디에 남겨 두어야 다음에 켜도, 다른 사람의 폰에서도 같은 값이 보이는가** — 그 "어딘가"가 DB다.

지금 `app/lib/services/mock_data_service.dart` 는 값을 컴퓨터 메모리에만 들고 있어서 새로고침하면 사라진다. 3주차에 이것을 Firestore로 바꾸는 순간, 처음으로 "진짜 DB"를 쓰게 된다.

DB는 크게 두 종류다.

| 종류 | 대표 | 데이터 모양 | 이 프로젝트 |
|------|------|-----------|-----------|
| **NoSQL (문서형)** | Firestore, MongoDB | 컬렉션 안에 문서(JSON 덩어리) | **지금 쓴다** (3주차~) |
| **SQL (관계형)** | PostgreSQL, MySQL, SQLite | 표(테이블) + 행 + 열, 표끼리 연결 | 나중에 (앱이 안정된 뒤) |

## 1단계. Firestore 기본 (3~5주차, 로그인·공지·벌점 만들 때)

### 배울 것
1. **컬렉션 / 문서 / 필드** — 엑셀로 치면 시트 / 행 / 칸. `개발기획서.md` 5번 표가 그대로 이것이다.
2. **CRUD 4가지** — Create(추가), Read(읽기), Update(수정), Delete(삭제). 모든 DB 작업은 이 4개다.
   - 공지 등록 = Create, 공지 목록 = Read, 공지 수정 = Update, 공지 삭제 = Delete
3. **문서 ID** — 문서마다 붙는 고유한 이름. 학생 문서의 ID를 Firebase 로그인 uid와 같게 만들면 "로그인한 사람이 누구인지"와 "그 사람의 정보"가 바로 연결된다.
4. **실시간 읽기(snapshot)** — 한 번 읽고 끝이 아니라, 값이 바뀌면 자동으로 다시 알려 준다. 선생님이 벌점을 주면 학생 화면이 저절로 바뀌는 이유.
5. **Firebase 콘솔로 데이터 직접 보기** — 앱을 켜지 않고도 웹에서 컬렉션을 열어 값이 들어갔는지 확인한다. **디버깅의 절반은 여기서 한다.**

### 직접 해보기 (3주차 첫 세션)
- [ ] Firebase 콘솔에서 `notices` 컬렉션에 공지 문서 1개를 **손으로** 만든다
- [ ] 앱에서 그 공지가 보이는지 확인한다
- [ ] 앱에서 공지를 하나 등록하고, 콘솔에 문서가 생겼는지 확인한다
- [ ] 콘솔에서 제목을 고치고, 앱 화면이 새로고침 없이 바뀌는지 본다 (실시간 읽기 체험)

### 이 단계에서 이해해야 하는 한 문장
> "화면은 DB를 비추는 거울이다. 데이터를 바꾸면 화면은 따라온다."

## 2단계. 데이터 설계 감각 (6~9주차, 도시락·질문·민원 만들 때)

### 배울 것
1. **참조(연결)** — 벌점 문서에 학생 이름을 통째로 넣지 않고 **학생 uid만** 넣는다. 이름이 바뀌어도 한 곳만 고치면 되기 때문. 이것이 DB 설계의 핵심 감각이다.
2. **중복 저장의 장단점** — 반대로 도시락 신청 문서에는 메뉴 이름을 그대로 넣어도 된다. 그날 메뉴는 바뀌지 않고, 매번 메뉴 문서를 따로 읽으면 느리기 때문. **"바뀌는 값은 참조, 안 바뀌는 값은 복사"**
3. **쿼리(조건 검색)** — "이 학생의 벌점만", "오늘 날짜의 도시락 신청만", "상태가 대기인 질문만". `where`, `orderBy`, `limit` 세 개면 이 앱의 모든 목록을 만들 수 있다.
4. **인덱스** — 조건 2개 이상으로 검색하면 Firestore가 "인덱스를 만들라"는 오류를 낸다. 오류 메시지에 있는 링크를 누르면 끝. 무서워하지 말 것.
5. **시간 다루기** — 날짜는 문자열이 아니라 `Timestamp`로 저장한다. 그래야 "오늘", "이번 주", "정렬"이 된다.
6. **트랜잭션의 개념만** — 도시락 마감 처리처럼 "여러 문서를 한 번에, 전부 성공 아니면 전부 취소"가 필요한 경우가 있다는 것만 알아 둔다.

## 3단계. 보안 규칙 (10~11주차, 배포 전 필수)

### 배울 것
1. **Security Rules가 하는 일** — 앱 코드가 아니라 **DB 문 앞에서** "이 사람이 이 문서를 읽어도 되는가"를 검사한다. 앱 코드를 뜯어 고친 사람도 여기서 막힌다.
2. **역할 기반 규칙** — 로그인한 uid로 `users` 문서를 읽어 role이 teacher면 전체 허용, student면 자기 uid 문서만 허용.
3. **규칙 테스트** — 콘솔의 "규칙 플레이그라운드"에서 "학생 A가 학생 B의 벌점을 읽으려 한다"를 시뮬레이션해 **거부되는지 확인**한다.
4. **개발 중 흔한 함정** — 처음에 편하게 "전부 허용"으로 열어 두고 배포까지 잊는 것. **배포 전 체크리스트에 반드시 넣는다.**

### 직접 해보기
- [ ] 학생 계정으로 로그인해 다른 학생의 벌점을 읽는 코드를 AI에게 한 줄 만들어 달라고 하고, **실제로 거부되는지** 본다
- [ ] 규칙 플레이그라운드에서 같은 시나리오를 돌려 본다

### 이 단계에서 이해해야 하는 한 문장
> "미성년자 정보를 다룬다. 규칙이 막아 주는지 확인하는 사람은 나다."

## 4단계. SQL 맛보기 (12주차 이후, 앱이 안정된 뒤 — 선택)

Firestore만으로 이 앱은 완성된다. 그러나 **일반 회사·서비스의 대다수는 SQL DB**를 쓰므로, 개발을 계속할 생각이라면 배워 두면 좋다. Firestore를 이미 써 봤기 때문에 훨씬 빨리 이해된다.

### 왜 배우나
- 통계("벌점 상위 10명", "월별 도시락 신청률")는 SQL이 훨씬 쉽다. Firestore는 집계가 약하다.
- 나중에 학원이 커져 회계·출결·성적까지 붙이면 표끼리 연결하는 SQL이 유리하다.

### 배울 것 (순서대로)
1. **표(테이블) 만들기** — Firestore 컬렉션을 표로 옮겨 본다. `students`, `penalties` 표. 열 이름과 타입 정하기.
2. **SELECT / WHERE / ORDER BY** — Firestore 쿼리와 1:1로 대응된다. 이미 아는 개념이다.
3. **JOIN** — Firestore에서 "벌점 문서의 uid로 학생 문서를 따로 읽던 것"을 SQL은 한 문장으로 붙인다. **Firestore의 불편함을 겪은 뒤 배우면 왜 필요한지 바로 안다.**
4. **GROUP BY와 집계** — 학생별 벌점 합계, 날짜별 신청 수. 통계 화면의 핵심.
5. **기본 키 / 외래 키** — 2단계의 "참조" 개념을 DB가 강제해 주는 장치.
6. **정규화의 감각** — "같은 정보를 두 곳에 적지 말라"를 규칙으로 만든 것. 1~3 정규형까지만.

### 연습 환경 (설치 부담 순)
1. **SQLite** — 파일 하나가 DB. 설치 거의 없음. VS Code 확장 "SQLite Viewer"로 바로 연습.
2. **Supabase(PostgreSQL)** — 무료 클라우드. Firebase와 비슷한 콘솔이 있어 비교하며 배우기 좋다.
3. 로컬 PostgreSQL 설치는 필요해질 때.

## 5단계. 그다음 (필요할 때만)

- **백업과 복구** — Firestore 내보내기, 실수로 지운 데이터 되살리기
- **비용** — Firestore는 "읽기 횟수"로 과금된다. 실시간 리스너를 화면마다 열어 두면 읽기가 폭증할 수 있다. 콘솔 사용량 그래프 보는 법.
- **마이그레이션** — 필드 이름을 바꾸거나 구조를 고칠 때 기존 데이터를 옮기는 법
- **ORM / 쿼리 빌더** — SQL을 코드로 다루는 도구. 서버 코드를 직접 쓰게 되면 그때.
